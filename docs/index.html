Which Content Pages Should You Refresh First?

A transparent baseline, a validated model, and an honest comparison of what happens when you check your own rules instead of trusting them.

Lateephah· FlyRank ML Internship — Applied Search Intelligence System· 2026

Abstract

Content teams often decide what to refresh using hand-picked rules — is a page stale? does it still get traffic? — without checking whether those rules actually predict decline. Using 30,000 pseudonymized pages across 32 clients from the FlyRank ML Internship dataset (trailing-90-day search and engagement metrics), I built a transparent two-signal rule as a baseline, audited it for measurement traps, then trained a Logistic Regression model validated under a client-grouped holdout designed to test generalization to a brand-new client. The rule looked strong on its own tuning population (precision@20 of 0.650) but fell to base rate on entirely unseen clients, while the validated model held precision@20/50/100 of 0.650/0.640/0.670 on that same honest split — a gap that only became visible by deliberately comparing a naive random split against the grouped one. The output is a ranked, reason-coded content-review queue with content archetypes, a human-review checklist, and an explicit no-go list, built as decision-support for a content team's triage — not an automated publishing system, and not a claim about how any search engine ranks pages.

01

Introduction

A content team with a few thousand published pages and one afternoon a week for refresh work cannot manually review every page. Someone has to decide what gets looked at first — and in practice, that decision is usually a rule of thumb applied by eye: it's old, it still gets traffic, fix it.

An editor opens the CMS on a Monday morning. Thirty thousand pages, one afternoon, no way to check them all. The rule they've always used says "old and still visible" is worth a look — but nobody has ever measured whether that rule actually catches the pages that are declining, or just feels right.

This project treats that rule as a hypothesis rather than a given. It builds the rule properly, measures whether the signals behind it hold up on real data, and then asks a second, sharper question: once you've validated a rule, does a statistical model — trained on the same data, checked the same way — actually earn the right to replace it? The answer here is a qualified yes, and the qualification is the more interesting part of the story.

02

Data

The source is the FlyRank ML Internship starter dataset — 30,000 pseudonymized content pages across 32 clients, one row per page, with trailing-90-day search (GSC-style) and engagement (GA4-style) metrics. A larger, 78.8-million-row daily-grain warehouse also exists behind the same project; it was used earlier in this work to verify schema and grain assumptions, but the starter export is what this pipeline is built on, because its columns match the feature set the baseline and model both depend on.

Population

Two filters define the working population: impressions_90d > 0 (the page has real search visibility to judge) and content_age_days >= 90 (the page is old enough to have a genuine 90-day trend to measure). On this dataset, every one of the 30,000 rows already satisfies both conditions.

Excluded on purpose

trend_direction and trend_pct — the columns the target label is built from — and the raw *_last_30d / *_prev_30d windows those are computed from, are excluded from every feature set in this project. Section 3 shows what happens if they're added back in.

Public safety

client_id and content_id arrive pre-pseudonymized in the source data. They are used only to group the validation split — never as model features — and no client names, URLs, or raw search queries appear anywhere in this project or its repo.

03

Methodology

Label

is_declining_label = 1 where trend_direction == "down". This is a proxy, not a directly observed outcome — it's a rule applied to a 30-day-vs-prior-30-day impression comparison, and it is measurably noisier at low impression counts (see Limitations).

Baseline: a transparent rule

The baseline gates on two conditions: impressions_90d >= 500 (a reliability floor — a separate check found that traffic volume on its own does not predict decline in a usable direction, so it's used to keep measurements trustworthy rather than as a scoring signal) and days_since_last_update >= 90 (the threshold the large-sample buckets actually confirmed: pages at 91–180 days since update declined at 61%, against 51% for pages updated in the last 30 days). A below-tier-median click-through rate adds a secondary bonus to the score.

Building this rule surfaced a real data trap worth naming: rows with avg_position == 0 ("no position data") were silently sorting into the top position tier, which would have corrupted any CTR-vs-position comparison built on it. The rule's CTR check excludes those rows explicitly.

Model

Logistic Regression over 22 numeric and 10 categorical features — all current-state, trailing-90-day totals or point-in-time tiers, never a 30-day window. A Random Forest was trained alongside it as a stronger, less transparent comparison.

Validation design

The split is a GroupShuffleSplit (80/20) grouped by client_id, holding entire clients out rather than individual pages. This choice is not cosmetic: a naive random row split let 31 of the 32 clients appear in both train and test, and it inflated every metric — ROC-AUC of 0.704 against the grouped split's honest 0.577, precision@20 of 0.900 against 0.650. Figure 2 shows this side by side.

Leakage checks

Deliberately adding trend_pct — the literal column the label is thresholded from — back into the honest feature set pushed ROC-AUC from 0.577 to 0.989. Adding the raw 30-day windows pushed it to 0.836. Both confirm the checking method actually works, and that the real feature set used throughout this project is clean.

Read plainly: the rule that looked strong on its own tuning population in an earlier pass (precision@20 of 0.650, measured across all 30,000 rows it was built against) drops to base rate on seven completely unseen clients. Logistic Regression wins at every precision@K cut that matters for a queue an editor works top-down. Random Forest wins on whole-ranking measures — ROC-AUC and Average Precision — but loses to Logistic Regression specifically where it counts. Added complexity did not earn its keep here; the simpler, more readable model is the one this project recommends.

05

Limitations

  • Proxy label, not ground truth. is_declining_label is a threshold on a noisy 30-day swing. Error analysis found a false negative built on a single impression — a page with essentially no data carrying a confident label.
  • One held-out split. These numbers come from a single client-grouped 80/20 partition. That is real evidence, not a guarantee across every possible split; repeated group splits would strengthen the claim further.
  • Cross-sectional, one snapshot. Nothing here supports "refreshing this page will increase its traffic." The honest, decision-support form is: this page looks worth reviewing first, because…
  • Not yet validated on a brand-new client. The random-vs-grouped gap above is itself evidence that performance on a client outside this population should be treated cautiously until spot-checked locally.
  • Does not model a search engine's ranking algorithm. It models this portfolio's own observed performance patterns, nothing more.
  • No claims about specific AI writing tools. Which AI model or content-type category a page used showed up among the features the model leans on, but sample sizes per category are small and uneven — not sufficient evidence about any one tool's output quality.
06

Ranked recommendations

The deployed playbook retrains the validated Logistic Regression on the full population, attaches a reason code drawn only from actionable features (staleness, CTR, position, engagement, word count — never content type or which AI model wrote the page), and sorts by a value-weighted score rather than raw probability.

The single clearest finding in this section: the five pages with the highest raw decline probability all had zero clicks in 90 days. They cost nothing to leave alone. Re-ranking by probability × click-equivalent value produces a completely different top five, with zero overlap — the pages actually worth an editor's first hour.

Content archetypes

Steady & Visible

67% of pages

High impressions, recently updated, near-base decline rate. Routine monitoring — no urgent action.

Visible But Stale

31% of pages

Highest average impressions of any group, but ~106 days since update and the highest decline rate observed. The primary refresh target.

High-Engagement Niche

1.6% of pages

Lower volume, but CTR and engagement far above every other group. Worth protecting and studying, not refreshing.

Near-Zero-Data Edge Cases

0.4% of pages

Averaging 4 impressions per 90 days — any rate computed here is a measurement artifact. Excluded from automated scoring entirely.

Human review, required before any action

  • Confirm the page isn't already deprecated, redirected, or intentionally scheduled for removal.
  • Confirm the reason code holds up on a manual look — a "stale" read on a page updated just outside this snapshot's window is a stale read, not a stale page.
  • Confirm impressions and clicks aren't near the reliability floor before trusting any rate computed from them.
  • Rule out an expected seasonal dip before treating a page as declining.

What should never be automated

  • No auto-editing, auto-publishing, auto-redirecting, or auto-deleting content from this score alone — every action routes through a human editor.
  • No acting on Near-Zero-Data Edge Cases rows, automated or manual-priority — exclude them from the queue entirely.
  • No using content type or which AI model authored a page to justify deprioritizing that pipeline — sample sizes are too small and uneven to support that claim.
  • No treating "declining" as "will decline" — this system supports a decision, it does not predict one.

Monitoring and retrain triggers

Precision@20/50/100 should be re-measured monthly against newly-resolved pages and compared against the 0.650/0.640/0.670 established here; a meaningful drop is the signal to investigate. A shift in the population's 0.542 base decline rate signals either a real portfolio change or an upstream data change, either way worth checking before trusting the score again. Any client not represented in the training population should get a local spot-check before the queue is trusted for them, rather than waiting for the next quarterly retrain.
